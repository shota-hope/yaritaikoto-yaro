# 開発の進め方

このリポジトリでは、変更の目的と経緯をGitHubに残しながら、小さく実装して確認する。

## 基本方針

- プロダクト仕様・決定事項の正本は [`product.md`](product.md)。
- 実装はスマートフォンでの使いやすさを先に確認する。
- 1つのIssueでは、1つの目的または一緒に確認できる小さな範囲を扱う。
- IssueとPRは、後から目的と変更内容が分かる最小限の文章にする。
- `main`へ直接実装せず、作業ブランチからPRで取り込む。

## モデルとレビュー

- Issueを作る前に、`gpt-6-astra`・reasoning `medium` を使って作業内容を計画する。
- 計画は簡潔にまとめ、Issueへ記録する。この段階では実装を始めない。
- 計画をレビューし、利用者の承認を得てから実装へ進む。
- 承認後の実装は、`gpt-5.6-sol`・reasoning `medium` を使う。
- モデルやreasoningを自動で指定できない、または指定できたか確認できない場合は、別のモデルで代用せず、各段階を始める前に利用者へ確認する。

## 1回の開発の流れ

1. `gpt-6-astra`・reasoning `medium` で作業内容を計画する。
2. 計画をまとめた短いIssueを作る。
3. 計画のレビューと承認を受ける。
4. `gpt-5.6-sol`・reasoning `medium` に切り替える。
5. `codex/<topic>` 形式の作業ブランチを作る。
6. 承認された範囲だけ実装し、仕様変更があれば `product.md` も更新する。
7. `npm test` と `npm run build` を実行する。
8. 主要な操作をブラウザで確認する。
9. 変更点を短く書いたPRを作り、Issueを `Closes #番号` で結びつける。
10. PRをsquash mergeし、作業ブランチを削除する。
11. ローカルの `main` を最新にする。

## Issueの書き方

目的、対象、完了条件だけを書く。調査メモや実装の細部は必要になった時点で追記する。

```md
タイトル: 端末内保存のプロトタイプを作る

年齢入力から達成までを端末内保存で試せるようにする。

- 年齢と時間の目安
- やりたいことと次の一歩
- 達成と再読み込み後の保持

テストと本番ビルドが通れば完了。
```

## PRの書き方

- タイトルは、利用者またはプロダクトに起きる変更を一文で書く。
- 本文は主な変更を数項目に絞る。
- 関連Issueを `Closes #番号` で記載する。
- 大きな変更は無理に1つのPRへまとめない。

## 完了の目安

- Issueの目的を満たしている。
- スマートフォン幅で主要操作ができる。
- 入力内容や既存データを壊さない。
- テストと本番ビルドが通る。
- 仕様や決定が変わった場合、文書も更新されている。
