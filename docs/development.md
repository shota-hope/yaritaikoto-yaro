# 開発の進め方

このリポジトリでは、変更の目的と経緯をGitHubに残しながら、小さく実装して確認する。

## 基本方針

- プロダクト仕様・決定事項の正本は [`product.md`](product.md)。
- 実装はスマートフォンでの使いやすさを先に確認する。
- 機能の追加・変更は機能ごとにIssueを作り、1つの目的または一緒に確認できる小さな範囲を扱う。
- 運用ルールだけを直す小さな文書修正は、Issueを作らずに進めてよい。
- IssueとPRは、後から目的と変更内容が分かる最小限の文章にする。
- `main`へ直接実装せず、作業ブランチからPRで取り込む。

## UIを一緒に詰める進め方

- 最初に、利用者がどうしたいか、現在の画面のどこが気になるかを聞く。エージェントだけで改善の方向や優先順位を決めない。
- UIの変更は、実装前に画像の画面案を提示する。スマートフォンを基準に、配置・文言・情報量・操作の流れを見て話せる状態にする。
- 利用者の感想を聞き、画像を修正するやり取りを繰り返す。近づいた部分は保ち、指摘された部分を調整する。
- 画像中のサンプルデータや細部を、そのまま確定仕様とは扱わない。合意した内容と未決事項を `product.md` に記録する。
- 方向が決まったら短いIssueにまとめ、計画の明示的な承認後に実装する。画像への好意的な感想だけで実装開始とは判断しない。
- 実装後は実際のブラウザで表示と操作を確認し、画像だけでは分からない使い勝手もレビューする。

## 機能開発の流れ

1. `gpt-6-astra`・reasoning `medium` で作業内容を計画する。
2. 計画をまとめた短いIssueを作り、その時点で利用者へレビューを依頼する。
3. 計画の承認を受けるまで実装しない。
4. `gpt-5.6-sol`・reasoning `medium` に切り替える。
5. `codex/<topic>` 形式の作業ブランチを作る。
6. 承認された範囲だけ実装し、仕様変更があれば `product.md` も更新する。
7. `npm test` と `npm run build` を実行する。
8. 主要な操作をブラウザで確認する。
9. 変更点を短く書いたPRを作り、Issueを `Closes #番号` で結びつける。
10. PR作成後、マージ前に利用者へレビューを依頼する。
11. PRの承認を受けるまでマージしない。
12. 承認後にPRをsquash mergeし、作業ブランチを削除する。
13. ローカルの `main` を最新にする。

## Issueの書き方

機能の追加・変更について、目的、対象、完了条件だけを書く。調査メモや実装の細部は必要になった時点で追記する。運用ルールだけを直す小さな文書修正では、Issueを作らなくてよい。

```md
タイトル: 端末内保存のプロトタイプを作る

年齢入力から達成までを端末内保存で試せるようにする。

- 年齢と時間の目安
- やりたいことと次の一歩
- 達成と再読み込み後の保持

テストと本番ビルドが通れば完了。
```

## PRの書き方

- タイトルは、利用者またはプロダクトに起きる変更を一文で書く。
- 本文は主な変更を数項目に絞る。
- 関連Issueがある場合は、`Closes #番号` で記載する。
- PR作成後、マージ前に利用者へレビューを依頼し、承認されるまでマージしない。
- 大きな変更は無理に1つのPRへまとめない。

## CIと自動デプロイ

- `main`向けのPRでは、GitHub Actionsが`npm ci`、`npm test`、`npm run build`を実行する。PRを更新すると古い実行は取り消し、新しいコミットを検証する。
- `main`へのpushでも同じ検証を行い、成功した最新コミットだけを既存のCloudflare Worker `yaritaikoto-yaro`へ公開する。複数の公開は直列に実行する。
- PRの検証にはCloudflareの認証情報を渡さない。公開時だけ`production` Environment Secretsの`CLOUDFLARE_API_TOKEN`と`CLOUDFLARE_ACCOUNT_ID`を使用する。
- `CLOUDFLARE_API_TOKEN`には、対象アカウントへWorkersを公開できる最小限の権限を設定する。値をリポジトリやログへ記載しない。
- `production` Environmentは`main`だけに限定し、`main`はPRと`verify`の成功を必須にする。force pushとブランチ削除は許可しない。
- workflowで利用するGitHub Actionsは、確認済みの完全なコミットSHAへ固定する。更新時は公式リポジトリのタグが指すコミットを確認する。
- GitHubのActions画面で検証・公開結果を確認する。失敗した場合は原因を修正してPRを更新し、`main`の失敗は修正PRをマージして再実行する。
- PRのマージ承認には、その変更が検証成功後に自動公開されることへの承認も含む。自動公開を止める必要がある場合は、マージ前にこのworkflowを変更する。

初回設定では、GitHubリポジトリのSettings > Environments > productionに次のEnvironment Secretsを登録する。

| Secret | 設定する値 |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | 対象アカウントに限定したWorkers公開用APIトークン |
| `CLOUDFLARE_ACCOUNT_ID` | 既存Workerが所属するCloudflareアカウントID |

Secretsが未設定または無効な場合、検証までは成功しても公開は失敗する。実際の公開URLはActionsの実行結果またはCloudflare Dashboardで確認する。

## 完了の目安

- Issueの目的を満たしている。
- スマートフォン幅で主要操作ができる。
- 入力内容や既存データを壊さない。
- テストと本番ビルドが通る。
- 仕様や決定が変わった場合、文書も更新されている。
